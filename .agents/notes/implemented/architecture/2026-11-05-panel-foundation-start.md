# Agent Note: panel.foundation-start —— 立项之后一键开工

Status: implemented

## Problem

`runtime.session-binding` 落地后，面板会正确显示「已立项，还没有基础设定」，但这一屏是死路：它只告诉作者「让本会话跑一遍基础设定，再来这里确认」，没有给任何动作。作者必须切回「对话」，再把「开始写基础设定」这句话打一遍。

同一块面板在相反的一端已经有动作：`panel.gate-resume` 让「认可」一次点击就把「继续」投回会话。立项后的开工是它的对称缺口——身份已经写好，只差一个把会话叫醒的入口。

约束：面板读不到 `work.json` 正文（文件资源通道只给存在性），所以按钮不能带书名、也不能替作者补参数；它只能是一个触发器。

## Decision

### 只在「已立项、还没有基础设定」这一屏给按钮

判据用已有的三个探针：

- 通道不可用或在加载 → 不给按钮（现状）。
- 身份缺（`work.json` 探针不是 `live`）→ 不给按钮：还没立项时没有可开工的作品。
- 有基础设定（任一锚点 `live`）→ 这一屏给的是作者确认闸门，不给开工按钮。
- 只有「身份在、两个锚点都不在」时渲染「开始基础设定」。

视图本身只在 `see-dsh-novel` 预设的会话里注册，所以这里不再重复判预设；会话绑定缺失由 `start` 返回 `'failed'` 走失败文案，不单独隐藏按钮。

### 一次点击：投一条开工指令

`StoryView` 里新增一个与「认可」并列的动作：点「开始基础设定」→ 调注入面的 `start(sessionId, cwd)` → `prompt([{ type: 'text', text: START_TEXT(cwd) }], 'queue')`。作者只点一次。

`START_TEXT` 做五件事：

1. 说明这是作者在面板上点的，并给出面板看到的工作区路径（来自会话列表的 `cwd`）；
2. 先 `story_work_show`，并把读到的工作区与路径核对——读不到或不是同一个目录就停下并告诉作者。面板按会话记录目录探针、工具按当前工作目录解析，两者可能指向不同作品，不核对就会把设定写进另一本书；
3. 再用 `story_next` 核对阶段：**不是 `foundation` 就停手并报告**（`unbound` 说明还没立项，`draft`／`ready` 说明设定已经在写或已写完），不要重复写；
4. 阶段是 `foundation` 时按真实顺序写：`story_foundation_outline` → `story_foundation_details` → `story_foundation_cast_index` → `story_foundation_cast_documents`；
5. 写完停在作者确认闸门前，**不要自行签核**——门禁不会因为这条消息放松。

第 3 条是**提示级缓解**（prompt-level），不是写入门禁：`story_next` 是路牌，`story_foundation_*` 也没有阶段前置条件（`tools.ts` 里四个工具不看身份文件与阶段），忽略第 3 条的模型仍可能把同一套设定再写一遍。面板的防重只在本次挂载内有效，重挂之后按钮会回来；这里能保证的是「指令里写明了停手条件」，不是「重复一定不会发生」。真正的写入门禁目前没有登记的能力行；需要时另开一行，不并进本行。

不带书名与章数：面板读不到，agent 用 `story_work_show` 一次就能读到准确值；带错反而误导。

### 写的过程中面板要挡住闸门

大纲是第一个落盘的文件，`story_foundation_outline` 一写，`story_frame.md` 就存在，面板的锚点立刻翻成「有基础设定」。若不做处理，作者会在设定只写了一半时看到闸门并可能点「认可」——那条回执绑定的是半套文件的摘要，后面几个文件一写摘要就变，确认作废。

挡住它的是**会话的运行状态**，不是「写完」这个猜出来的信号：`SessionSummary.running` 已经随会话列表一起进来，视图现在就在读它。规则按优先级从高到低：

1. `running` 为真：「会话正在运行，结束后这里会按实际文件重新判定。」这一行压过其它一切——空态屏不渲染开工按钮、也不显示「让本会话跑一遍」那句死路文案；闸门屏不渲染三个确认按钮。作者在别的标签页看不到「可以认可」的假象，也不会排出第二轮开工。`running` 是**会话级**信号，可能是任何一轮（包括作者自己在对话里补的「开始写」），所以它不清除 `start-unknown`，也不作为「开工指令送达」的证据。
2. `started`（`prompt` 成功、`running` 还没被观察到）：「已开始基础设定…」，不渲染任何按钮；观察到 `running` 为真后由第 1 条接管。
3. `start-unknown`（`prompt` 抛错）：只管空态屏——不渲染开工按钮，文案见下一节；它不随 `running` 解除，也不压过闸门屏（一旦探针看到基础设定，闸门照常显示，那里本来也没有开工按钮）。
4. `running` 从真变假（观察到这一轮开始、又结束）：清除 `started`，面板回到探针判定——两个锚点里任一存在就落在闸门屏。如果那一轮中途出错或作者按了停止，作者看到的是「有基础设定」的闸门，与手动写了一半的状态一致，而不是被面板藏起来。

`started` 与 `start-unknown` 都是组件实例上的本地状态，不落盘、不广播；切换会话时随其它本地状态一起重置。`start-unknown` 没有「刷新后仍然记得」的保证，重挂之后按钮会回来；重复投递由 `START_TEXT` 的阶段检查缓解（提示级，见上）。

### 失败与防重复

- `start` 返回 `'failed'`（无绑定，或 `prompt` 返回的 `RemoteResult.ok !== true`）是**确定的失败**：回到空闲态，文案「已立项，但没能自动开始；在「对话」里说一句「开始写基础设定」即可。」，按钮恢复可点。
- `prompt` 抛错是**结果未知**：请求可能已经在宿主侧被接受，再点一次会排进第二轮。这种情况进入 `start-unknown` 状态，文案「没能确认会话是否收到开工指令：先看「对话」里有没有新的一轮；没有的话直接在对话里说一句「开始写基础设定」。」，不渲染开工按钮——不确定时不在面板上重复投递；出口是对话，不是刷新。
- 提交期间按钮置灰；同帧连点用 ref 挡住；切换会话时丢弃在途结果（沿用 `currentSession` 栅栏）。

### 注入面

`ViewInjected` 增加 `start(sessionId: SessionId, cwd: string | undefined): Promise<ResumeOutcome>`（复用 `'ok' | 'failed'`），`index.ts` 里与 `resume` 并列实现，共用同一条 `prompt(..., 'queue')` 路径；抛错不吞，由视图映射成 `start-unknown`。`RESUME_TEXT` 与 `START_TEXT(cwd)` 都由 `index.ts` 导出；文本的稳定语义按「验收」第一条断言，不锁整句。

## Alternatives considered

**信任「写完」再把闸门放出来，不改渲染分支。** 少一个状态。否掉：锚点在大纲落盘那一刻就翻，作者能在半套设定上点认可，摘要随后失效——这比多一个状态糟得多。

**把「开始基础设定」做成斜杠命令（`/story-start`）。** 面板与命令入口统一。否掉：命令是 `runtime.commands` 那一行的交付；而且命令仍要作者去对话里输入，没有解决「面板是死路」。

**把按钮做成「跳到对话页」。** 零投递风险。否掉：只是换个地方让作者再打一遍字，没省任何一步；面板有 `session.prompt` 这条通道。

**在消息里带上书名与目标章数。** 信息更全。否掉：面板拿不到正文，只能靠猜；agent 用 `story_work_show` 就能读到准确值。

**开工失败也锁死按钮。** 与认可一致。否掉：认可失败意味着回执已写下、重复点击会写两条；开工失败什么都没发生，锁死只会让作者重开会话。

## Consequences

`src/client/index.ts` 导出 `START_TEXT(cwd)` 并给视图注入 `start(sessionId, cwd)`：`prompt([{ type: 'text', text }], 'queue')`，无绑定或 `RemoteResult.ok !== true` 返回 `'failed'`，抛错不吞、由视图映射成结果未知。`StoryView.tsx` 的 `Phase` 扩到 `idle`／`submitting`／`resumed`／`resume-failed`／`started`／`start-unknown`，空态屏在「通道可读、身份在、两个锚点都不在」时渲染「开始基础设定」；闸门屏与空态屏都按 `running` → `started` → 其余的顺序决定显示，`running` 为真时两屏都只显示「会话正在运行…」且不渲染任何按钮。`started` 由「见过这一轮跑起来、又结束」收尾（`sawTurn` ref），回到探针判定；`start-unknown` 只管空态屏，不随 `running` 解除。切换会话重置本地状态，在途结果用 `currentSession` 栅栏丢弃。

验证见 `test/client.test.mjs`（开工按钮的可见条件与一次点击、确定失败可重试与结果未知不给按钮、`running` 抑制两类按钮、`started` 在观察到的一轮结束后解除、身份缺时没有按钮、`START_TEXT` 的稳定语义、`start` 注入面的 payload／`queue` 模式与无绑定失败），真实运行回执由 Verify 阶段写到 `artifacts/real-runs/panel.foundation-start.json`。

代价与已知限制：

- 开工消息是作者口吻：会话记录上看起来像作者打的字，导出时要知道这条是面板代发的（与 `panel.gate-resume` 同一限制）。
- 面板不能显示书名，按钮只能写「开始基础设定」；作者想确认是不是这本书，要回对话或看工作区路径。
- `running` 是会话级信号，不是「这一轮是基础设定」的信号：若作者在开工轮之后立刻说了别的，`started` 解除后落在闸门屏，仍在正确的时点。
- 这条消息会触发一整轮基础设定写作（四个工具、多张角色卡），耗时与 token 由这一下点击决定；中断走宿主的停止按钮。
- 面板按会话记录目录探针、工具按当前工作目录解析，两者可能指向不同目录；消息里的 `story_work_show` + `cwd` 核对是兜底，agent 对不上就停。
- 重复投递只有提示级缓解：重挂后按钮回来、模型也可能忽略阶段检查；foundation 工具没有阶段前置条件，真正的写入门禁没有登记的能力行，需要时另开一行。
