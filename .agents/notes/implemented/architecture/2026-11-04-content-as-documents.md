# Agent Note: 作品内容落盘为文档，SQLite 只做索引

Status: implemented

## Problem

「作品内容存哪里」决定导出、备份、恢复、检索与跨作品隔离的实现方式。把正文放进数据库最省事，但导出要重写序列化，作者也无法直接查看或 diff 正文；只留文档又会让检索与状态投影每次都全量扫描。

## Decision

一个工作区就是一部作品。

作品正文与设定以文档形式落盘，与参考工程一致：可直接阅读、可 diff、可直接导出。SQLite 一作品一库，只保存索引——检索、投影、状态缓存等派生数据。索引不是正文的唯一副本，删除后能从文档重建。

一作品一库指库文件属于该作品的工作区，不跨作品共享；作品之间的隔离由工作区边界保证，不靠库内的一张作品表。

## 权威与重建

文档是权威，索引是派生。二者不一致时以文档为准，由 `runtime.recovery` 重建索引；`state.check` 的对账结论也只读文档与状态，不回写正文。

## Alternatives considered

**全部内容进 SQLite。** 事务与一致性最省心，查询统一。否掉的原因是正文一旦只在库里，导出要重建序列化、作者无法直接查看或 diff、损坏时无法靠文本恢复；把可读性交给导出工具，等于把作品的可恢复性押在一个未写的导出函数上。

**纯文档、不建索引。** 最贴近「一个工作区一部作品」的直觉，也没有双写不一致。但每次检索、状态投影与面板加载都要全量扫描并解析文档，章节数上去后不可接受。

**全局单库，按作品 ID 隔离。** 备份与跨作品检索更集中，但一个库承载所有作品，单作品导出、恢复与损坏隔离都要额外实现，且违背一工作区一作品的边界。

## Consequences

收益：正文始终可读、可 diff、可单独导出；索引损坏可从文档重建；备份只要打包工作区目录；作品隔离与文件系统边界一致，不用在库层再实现一次。

代价：双写需要一致性策略——文档变更后必须让索引失效或重建，否则检索会读到旧内容；「一作品一库」让跨作品检索必须逐库打开，不能一条 SQL 扫全库。文档格式一旦确定就构成对外契约，改名与迁移要按能力交付。
